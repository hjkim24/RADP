### 워크스트림별 진행 (§2)

> **흐름 고정.** 이번 주에 새 기술이 처음 들어간다. 순서를 바꾸지 마라 —
> 기존 방식의 한계(a) → 새 기술 원리(b) → 대가를 포함한 비교(c) → 적용 범위(d)
> → 실측(e, f). 비교나 숫자를 원리보다 앞에 두면 청중이 모르는 것을 평가하게 된다.

**1. RADP — c. 공짜 아님 — 3종 장단점** (P4 표)

| | full-replay | surgical | parity |
|---|---|---|---|
| 복구 시 재계산 | 체인 전체 | 죽은 stage | **없음** |
| 복구 후 KV | 전부 재계산값 | 죽은 stage만 재계산값 | **원본 비트 그대로** |
| P 1개당 추가 비용 | 164 ms | 16 ms | **0.87 ms** |
| 정상 운영 추가 비용 | 없음 | 입력 미러 | 입력 미러 + **KV 컬럼 전송** |
| 적용 범위 | 전부 | 전부 | non-head + downstream 생존자 필요 |

→ 표 아래 결론 한 줄: **장애 시점 비용을 정상 운영 중 네트워크 세금과 맞바꾼 것**

**1. RADP — d. 적용 범위를 첫 워커 밖으로**

- 라벨 3줄:
  - 앞선 생존자가 한 칸 앞서 slot 어긋남 → `min`으로 잘라 정렬
  - 구현 중 chain 장애 표식이 다음 hop으로 덮어써지는 버그 발견함
  - 노드 3개 체인에서는 홉이 하나뿐이라 드러날 수 없던 버그
- 캡션: fleet 기준 on-1 · on-6 · ao-1은 parity, tail on-2만 폴백

**2. Measurement — a. 복구 시간이 장애 시점을 안 탐**
- 시각물: `paper/figures/fig_recovery_ttr_slide.png`
- 라벨 3줄:
  - P = 죽기까지 만든 토큰 수. 기울기 = P 1개당 추가 비용
  - full-replay 164 → surgical 16 → parity 0.87 ms/pos
  - parity만 기울기 ≈ 0
- 캡션: OPT-350M 24층 / 5-stage 이종 체인 / 15개 트라이얼 전부 유효
- 참고: 로그축임. 점선은 정상 decode 스텝 163 ms 기준선
- **용어 주의:** P는 *생성 진행도*(죽기까지 만든 토큰 수)지 파이프라인 stage 순서가 아님.
  victim 위치(어느 워커)와 헷갈리지 않게 발표에서 한 번 짚어라

### 한계 (반드시 슬라이드에 올릴 것)

§11 — 한계를 빼지 않는다. 위 워크스트림 슬라이드의 남는 자리에 붙이거나 한 장을 따로 잡아라.

- tail victim은 여전히 surgical 폴백. downstream 생존자가 없어 게이트가 걸림.
  `count−1` 규칙이면 덮이나 과소추정 시 잘린 KV 설치 위험 → 미검증 규칙 대신 폴백 유지
- KV shipping 비용은 c 슬라이드 표에 이미 있음. 여기서는 **정량화 안 했다**는 것만 덧붙임
- prefill(position 0) 장애는 재계산 0 아님
- **선행연구:** KV parity 자체는 GhostServe가 먼저 함. 우리 기여는 기법 발명이 아니라
  **datacenter 기법을 이종 edge 체인 regime으로 옮겨 측정한 것**. 이 문장 그대로 올려라
