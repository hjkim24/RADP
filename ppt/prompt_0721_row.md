# 0721 덱 — 장단점 표에 행 하나 추가 (이것만 한다)

**슬라이드를 추가·삭제·재배치하지 마라.** 11장 그대로 둔다.
아래 한 가지 외에는 아무것도 건드리지 마라.

## 작업 — `c. 복구 알고리즘별 장단점` 표에 행 1개 삽입

`복구 시 재계산` 행 **바로 아래**에 새 행을 넣는다 (6행 → 7행):

| 항목 | full-replay | surgical | parity |
|---|---|---|---|
| 복구 후 KV | 전부 재계산값 | 죽은 stage만 재계산값 | **원본 비트 그대로** |

- 새 행도 기존 본문 행과 같은 서식: 16pt, `404040`, 배경 `E8EAF0`/`F6F7F9` 교대
  (행이 하나 늘었으므로 **삽입 지점 아래 행들의 교대 색을 다시 맞춘다**)
- parity 칸 `원본 비트 그대로`만 **굵게**
- 표 높이가 늘어 아래 결론 줄과 겹치면 표를 위로 늘리지 말고 **결론 줄을 아래로** 민다

## 왜 넣나 (발표 때 말할 것)

parity 를 지금까지 "더 빠름" 으로만 팔았는데, **재계산이 없다는 건 정합성 보장이기도 함.**

- XOR 복구에는 부동소수 연산이 하나도 없음 → 죽은 워커가 갖고 있던 **바로 그 바이트**가 복원됨
- surgical 은 미러 입력을 **backup 워커에서 다시 forward** → 수학적으로 같은 값이지만
  연산 하드웨어가 달라 마지막 비트까지 같다는 보장은 없음
- 이종 클러스터라 backup 이 다른 티어(AGX·CPU)일 수 있어 이 차이가 더 커짐

**과장하지 마라.** 실측 15/15 트라이얼에서 세 방식 모두 정상 실행과 토큰이 일치했음.
관측된 오차는 없음. 보장의 강도가 다르다는 얘기지, surgical 이 틀린 답을 냈다는 얘기가 아님.

근거: `tests/test_parity_recovery.py` 가 복원된 KV 가 victim 원본과 **bit-identical**
임을 layer 별 K·V 로 단언함. surgical 테스트에는 그 단언이 없음(출력 일치만 검증).

## 끝나고 확인할 것

- 표가 **7행 4열**인지
- 본문 행 배경이 `E8EAF0` / `F6F7F9` 로 규칙적으로 교대하는지
- 표와 결론 줄이 겹치지 않는지
- 슬라이드 수가 그대로 **11장**인지
