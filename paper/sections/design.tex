\subsection{Recovery-Aware DP ($\psi$+$R$ joint optimization)}\label{sec:design:dp}

% Outline (~0.7 page, the densest subsection — gets the equation
% block, the recurrence, and Algorithm 1):
% (a) State: $(j, s)$ — first $j$ layers placed across stages whose
%     last index is $s$. Cost function
%       rank(state) = (1-alpha) * sum_stage_time + alpha * max_stage_time.
%     alpha=0 -> EdgeShard latency mode. alpha=1 -> Jupiter throughput
%     mode (Eq. 11). The $\alpha$ knob is exposed at runtime as
%     `optimization_mode={latency, throughput, blended}` (Table or
%     inline list, not a full \S\S).
% (b) Recurrence: one equation block. Memory feasibility check folds
%     in $R$: stage primary memory + sum of backed-up peers' memory
%     <= device cap.
% (c) Recovery table $R$: greedy pass that minimizes
%     max(backup_memory_overflow) for a fixed $\psi$. The
%     alternating loop (Algorithm 1) provably converges in finitely
%     many iterations because cost is monotonically non-increasing
%     across alternations.
% (d) Complexity: $O(L^2 \cdot |D|)$ per inner DP. Brute force
%     over $|D|!$ device orderings is acceptable for the 3--8 device
%     edge fleets we target; a heuristic prune falls back to
%     $O(|D|^2)$ for larger fleets.

\subsection{Mirror cache and chain-aware recovery}\label{sec:design:mirror}

% Outline (~0.5 page, combines mirror + recovery into one section):
% (a) Problem statement: with sync chain forwarding the coord sees
%     only the chain head's input locally. A mid-chain death has
%     no activation history at the coord to replay onto the backup.
% (b) Fix: every worker fires a one-way MirrorActivation RPC to the
%     coord BEFORE running its stage. Coord stores in a position-keyed
%     cache (idempotent inserts handle duplicate retries and out-of-
%     order arrivals). Single-threaded mirror dispatcher per worker
%     keeps ordered delivery the common case; position keys handle
%     the rest.
% (c) Trailer-stamped attribution: when a worker's downstream
%     RunStage fails, it stamps the failed (start, end) onto the
%     gRPC trailer before aborting. Coord reads the trailer and
%     looks up the ORIGINAL placement (not the live execution
%     plan) — so the trailer names the truly-dead worker even when
%     heartbeat has already substituted the backup. This is the
%     missing piece in a chain where $R$ rerouted through a
%     surrogate.
% (d) Full chain replay vs stage-only: surviving upstream workers
%     already advanced their KV cache by one step on the failed
%     attempt. Naive retry double-counts. Evict + replay rebuilds
%     deterministically.

\subsection{Asynchronous chain forwarding}\label{sec:design:async}

% Outline (~0.5 page):
% (a) Sync chain's hidden cost: each in-flight stream occupies a
%     gRPC handler thread on EVERY chain stage until the nested
%     response unwinds. $C$ streams $\times$ $N$ stages =
%     $CN$ occupied slots. Throughput placement's pipeline
%     parallelism never materializes at $C \geq 4$.
% (b) Protocol: workers dispatch the next-hop RunStage to a bounded
%     thread pool and ACK to their upstream caller immediately. The
%     chain tail wakes the coord via CoordinatorService.ResultReady
%     when its work is done.
% (c) Per-(request_id, position) Event on the coord; _invoke waits
%     with a 30s timeout. Per-request lock on the worker so two
%     concurrent steps of the same request can't race on the same
%     DynamicCache.
% (d) Trade-off: trailer-based attribution unavailable in async
%     mode (the response chain unwound long ago). Heartbeat +
%     timeout-driven fallback. \S\ref{sec:eval:recovery} measures
%     the cost, \S\ref{sec:disc} discusses operator trade-off.
