\subsection{Pipeline-parallel inference on heterogeneous edge}

Pipeline-parallel LLM inference partitions a transformer model
along its decoder-block axis: each worker hosts a contiguous range
of layers (a \emph{stage}), and an inference request flows from
stage to stage as a stream of activation tensors. Each request
carries per-stage KV cache state that the stage owner updates
in place. The two phases of generation place very different
demands on the transport: prefill ships a single
$(S \times h)$-dimensional activation through the chain ($S$ is
the prompt length, $h$ the hidden dimension), while decode pushes
a single $(1 \times h)$ activation per generated token --- only
$8$\,KB at fp16 for OPT-6.7B's $h=4096$. A decode transfer is
$S$ times smaller than its prefill counterpart, but every generated
token still waits for the full stage chain.

Edge fleets can mix GPU tiers, memory capacities, and CPU-only
fallback devices. Our main deployment combines AGX Orin and Orin Nano
workers, while the cross-tier probe also uses CPU-only boards. A slow
stage stalls every downstream stage during autoregressive decoding, so
placement must account for both device speed and memory capacity.

Edge failures cannot be treated as a rare exceptional path. During
the measurement campaign behind this paper we
encountered internal-storage-induced file system failures on two boards,
sustained network partitions on three, and a worker simply not
coming back from a SIGTERM on one more. A placement strategy that
treats failure as an exceptional path --- restart from scratch on
\texttt{ECONNRESET} --- produces a system whose first worker
crash aborts every in-flight stream.

\subsection{Why the obvious composition of prior systems fails}

The natural recipe is to take EdgeShard's latency-optimal DP for
$\psi$ and bolt on Petals' swarm redundancy for $R$. Petals assumes
that every transformer block is hosted by several servers, so its
failed-stage replay requires duplicate block capacity somewhere in the
swarm~\cite{borzunov2023distributed}. That capacity is absent in our
memory-tight deployment: the 12.4\,GiB OPT-6.7B model already has to be
split across 8\,GB Orin Nano and 32\,GB AGX Orin workers, and reserving
another copy of a Nano's primary stage can make an otherwise valid
placement infeasible.

A second attempt --- Jupiter's throughput-optimal DP plus a
supervisor that restarts crashed workers --- also fails, but
differently. Jupiter's LLM-partition DP (Eq.~1
in~\cite{ye2025jupiter}) is the algorithmic starting point of our
$\psi$-recurrence, but it optimizes active-stage throughput without
recovery reservations. $\psi$ is computed
assuming all workers stay alive; backup memory is never
reserved, so when a Nano dies the supervisor has nowhere to load
its layers without exceeding a survivor's memory. \sys{} retains
both the slowest-stage and cumulative-latency objectives, enumerates
device subsets and orders, and alternates placement with recovery
mapping under Eq.~\ref{eq:mem}.

These compositions miss the same systemic point: on
memory-tight edge, $\psi$ and $R$ have \emph{coupled} feasibility
regions. The set of legal placements depends on which backups are
assigned because the backup memory is part of every device's cap
(\S\ref{sec:design:dp}, Eq.~\ref{eq:mem}). A cost-first placement
can therefore have no valid recovery mapping even though another
placement is protectable. \sys{} searches for a self-consistent
$(\psi,R)$ pair inside this coupled feasible set.
